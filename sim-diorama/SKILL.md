# Sim Diorama — 물어보고, 프롬프트 짜고, 직접 만들기

결과물 공식: **픽셀아트 무대 + 진짜로 계산되는 규칙 하나(눈에 보이는 증거 포함) + 서로 맞물리는 사람 루틴 + 상태 전환(낮밤·날씨) + 설명 패널**.
예시: Hearthblock(블록 마을), Twilight Marina GP(F1식 야간 레이스), Hollowmere(움직이는 계단이 있는 마법 성).
작품마다 첫 판 뒤에 여러 번 고쳤다. 그 고친 내용을 **첫 판 기본값**으로 바꾼 것이 `references/quality-bar.md`(완성도)와 아래 1·2단계(질문과 구조 확인)다.
**목표: 첫 판부터 사용자가 머릿속에 그린 것과 같은 구조 + Marina GP 최종판 수준의 완성도.**

## 단계

### 1. 물어보기 (한 번에, 짧게)
지금까지 만든 작품은 첫 판 뒤에 대부분 여러 번 고쳤다. 고친 이유를 모아 보면 **처음에 물었으면 막을 수 있었던 것**이 대부분이다.

| 작품 | 첫 판 뒤에 나온 요청 | 처음에 물었어야 할 것 |
|---|---|---|
| Twilight Marina GP (F1식 레이스) | "차가 너무 작아", "건물이 거의 없어 그 장소 느낌이 안 나", "피트 스톱이 너무 단순해", "밋밋해", "정보가 흩어져 있어", "쓰레드에 올리기 좋게", "불꽃을 계속 터뜨리게" | 주인공과 카메라, 꼭 있어야 할 명소, 단계별로 보여 줄 핵심 장면, 분위기, 화면 구성, 용도, 볼거리 |
| Hearthblock (블록 마을) | 첫 요청에 계산 규칙(블록 캐고 놓기)과 역할 5개, 밤 좀비까지 다 들어 있어 첫 판이 요청과 맞았음 | 진짜로 계산될 것, 사람 역할 — 이 둘이 처음에 분명하면 결과가 맞는다 |
| Hollowmere (움직이는 계단 성) | "구조가 참고 영상과 달라" ×4 | 참고 자료, 반복 구조, 기본 시점 |

그래서 사용자 말에서 아래 칸을 먼저 채워 보고, **비어 있거나 짐작이 갈리는 칸만** 묻는다.

1. 주제·장소 2. 주인공 3. 진짜로 계산될 것 4. 핵심 장면 5. 사람 역할 6. 꼭 있어야 할 명소·소품 7. 참고 자료 8. 분위기(시간대·색) 9. 화면 구성 10. 용도(웹 / 영상)

묻는 방법:
- 한 번에 최대 4개, 각 질문에 보기 2~4개 + 기타. 질문 도구(예: AskUserQuestion)가 있으면 그걸 쓰고, 없으면 번호 목록으로.
- 아래 순서로 우선순위를 둔다. 결과를 가장 크게 바꾸는 것부터다.
- 사용자가 "알아서"라고 하면 묻지 말고 채운 뒤 "제가 채운 칸"으로 표시한다.
- 보기는 **사용자가 말한 주제에 맞춰** 만든다. 아래 예시를 그대로 쓰지 않는다.

| 순서 | 묻는 것 | 질문 예 | 보기 예 (주제에 맞게 바꿔서) |
|:--:|---|---|---|
| 1 | 진짜로 계산될 것 | "가장 '진짜 계산되네' 싶어야 할 것 하나는?" | 레이스: 타이어 마모와 피트 전략 / 마을: 블록 수 장부 / 성: 계단 회전 물리 |
| 2 | 핵심 장면 | "단계별로 자세히 보여 줄 장면이 있나요?" | 피트 스톱 / 집 짓기 / 계단이 바뀌는 순간 / 없음 |
| 3 | 주인공과 카메라 | "화면이 주로 따라갈 대상은?" | 내 차 / 특정 사람 / 전체를 내려다보기 |
| 4 | 참고 자료 | "비슷한 사진·영상·장면이 있나요?" | 첨부 / 실제 장소 이름 / 영화·게임 속 장면 / 없음 |
| 5 | 꼭 있어야 할 명소 | 실제 장소를 말했을 때: "이 중 꼭 넣을 곳은?" | 그 장소의 대표 구조물 5~8개를 보기로 |
| 6 | 분위기 | "시간대와 색감은?" | 노을→밤 / 맑은 낮 / 비 오는 밤 / 따뜻한 촛불 |
| 7 | 용도 | "어디에 쓰나요?" | 웹에서 직접 놀기 / 쇼츠·릴스 영상 / 둘 다 |

용도가 영상이면 세로(9:16) 공유 화면과 7단계를 처음부터 염두에 둔다. 묻지 않은 나머지(사람 디테일, 빛, UI, 볼거리)는 `quality-bar.md` 기준으로 알아서 넣는다.

**특정 기존 작품·게임·실제 상표가 나오면**(해리포터, 마인크래프트, F1, 실제 경기장 등) 이름·고유 캐릭터·로고·공식 텍스처는 빼고 느낌만 살린 오리지널로 바꾸고, 바꾼 점을 한 줄로 알린다.

### 2. 참고 자료가 있으면: 구조부터 확인
만들기 전에 **무엇이 몇 개, 어떻게 이어지는지**를 말로 정리하고 사용자에게 맞는지 확인받는다. 이 단계를 건너뛰면 "구조가 다르다"로 몇 판을 버린다.
- 영상이면 1초에 2장씩 뽑아 한 장에 모아 본다(ffmpeg가 있을 때):
  `ffmpeg -i ref.mp4 -vf "fps=2,scale=480:-1,tile=4x4" -frames:v 4 ref-sheet-%d.png` + 핵심 장면은 원래 해상도로 몇 장 더.
- 실제 장소면 그 장소의 배치(무엇이 어디에, 무엇이 무엇 위로 지나가는지)를 정리한다.
- 정리 형식(3~5줄): 전체 모양 / 반복되는 단위 / 움직이는 부분과 그 범위 / 기본 시점.
  - 예(실제 장소): "섬 하나에 서킷 전체. 호텔이 트랙 위를 가로지르고, 피트 건물과 관중석이 메인 직선을 따라 있음. 한쪽에 요트 마리나, 반대쪽에 빨간 지붕 테마파크. 기본 시점은 내 차를 따라가는 아이소."
  - 예(영상 속 구조): "긴 빈 공간 양 끝에 네모 계단탑 2개. 움직이는 계단은 모서리를 축으로 90° 돌아 두 탑을 잇는다. 시점은 위에서 똑바로 아래."
- 사용자가 고쳐 주면 그 말을 그대로 프롬프트에 넣는다. 확인이 끝나기 전엔 만들지 않는다.

### 3. 프롬프트 짜기
`references/prompt-recipe.md`의 7덩어리 템플릿(⑦ Showcase 포함)과 체크리스트로 영어 프롬프트를 쓴다. 핵심 규칙:
- ④ "X is simulated, not animated" + 공식/숫자 + **화면에서 맞는지 확인되는 증거**(장부가 0으로 맞음, 점수 계산식, 예상 시간 vs 실제 시간 등).
- 사람은 3~5역할, 서로 의존하게(A가 만들어야 B가 쓴다, 없으면 기다린다).
- 실제 크기·개수를 숫자로. 사소한 행동 1~2개. 끝은 `Original fictional content only, English UI.`
- ⑦ Showcase는 사용자가 말하지 않아도 항상 넣는다(`quality-bar.md` A~G). 실제 장소를 말했으면 대표 구조물 5~8개를 이름 바꿔 다 넣는다.
- 2단계에서 확인한 구조 문장은 그대로 ③(무대)에 넣는다.
- 핵심 이벤트(사용자가 "완벽하게"라고 한 것)는 사람별 역할·단계·시각까지 쪼개 쓴다.

사용자에게 보여줄 것: 완성 프롬프트(코드블록) + "요청 → 프롬프트에서 한 일" 표 + 내가 채운 칸.
사용자가 "프롬프트만"이라고 했으면 여기서 끝낸다. 아니면 확인 묻지 말고 바로 4단계로.

### 4. 직접 만들기
`references/quality-bar.md`와 `references/build-playbook.md`를 먼저 읽고 그대로 따른다(품질 기준, 렌더 파이프라인, 시뮬 구조, 함정 목록). 막히면 `references/example-marina-gp.html`을 grep(통째로 읽지 말 것).
- 파일: 현재 작업 폴더 아래 `<slug>/<slug>.html` 한 장. three.js r128을 cdnjs에서.
- 반드시 `window.__sim = { setSpeed(n), jump(hour), state(), invariants(), fastForward(sec), cam(mode), share(on,aspect) }` 훅을 넣는다(검증·녹화용).
- 150KB가 넘어가면 고칠 때 `scripts/patch.py`(rep/cut 패치 파일)를 쓰고 버전별 백업(`<slug>.v2.html` …)을 남긴다.
- 페이지 기본: `<title>` 2~4단어, 색은 :root 토큰(+ 다크 모드), body 배경 지정, 휴대폰 폭(390px)에서 가로 스크롤 없음.

### 5. 검증 (헤드리스, 창 안 띄움)
스크립트를 처음 쓸 때 한 번: `cd <이 스킬 폴더> && npm install && npx playwright install chromium`
```bash
node <이 스킬 폴더>/scripts/verify.mjs <html경로> <출력접두사>
```
낮 → 8배속 → 밤으로 넘기며 스크린샷 3장, `state()`, `invariants()`, 콘솔 에러를 찍는다.
스크린샷은 직접 열어 본다. 확인할 것: 에러 0(ReadPixels GPU 경고는 무시), 불변식 전부 true, 사람들이 실제 할 일을 하고 있음, 움직여야 할 것이 **전부 한 번 이상 실제로 움직였음**, 밤 이벤트가 실제로 일어남, 화면이 빈칸·검정이 아님.
실패하면 고치고 다시 돌린다. 수치(속도·확률·체력)가 지루하거나 너무 쉬우면 조정한다.
그다음 `quality-bar.md` 끝의 검사 질문을 스크린샷으로 확인한다: 기본 화면·전체 보기·밤·SHARE 9:16·휴대폰 폭 390px. `__sim.share(true,'9:16')`, `__sim.cam('over')`로 바꿔 찍는다.
playwright를 못 쓰는 환경이면 사용자에게 파일을 브라우저로 열어 달라고 하고, 위 항목을 체크리스트로 준다.

### 6. 전달하고 다듬기
- 파일 경로와 여는 법(`open <파일>` / 브라우저로 끌어다 놓기)을 알려 준다. 쓰는 환경에 웹에 올리는 도구가 있으면(예: Claude 아티팩트) 그걸로 올려 링크를 줘도 된다.
- 사용자 언어로 보고: 들어간 것(사람별 일, 진짜 계산 규칙, 밤·날씨, 조작법) · 검증 결과(실제 숫자) · 아직 거친 점 · 바꿀 수 있는 것 제안.
- 마지막에 **비교 질문 하나**를 던진다: "머릿속 그림과 가장 다른 곳이 어디인가요?" 보기: 크기·카메라 / 배경·밀도 / 구조 / 핵심 장면 / 분위기 / 화면 정리(실제로 고친 요청에서 나온 축들). 답을 받으면 그 축만 고친다. 다른 곳은 건드리지 않는다.

### 7. (요청 시) 쇼츠 영상 찍기
필요한 것: playwright(5단계에서 설치) + ffmpeg.
"쓰레드/인스타에 올릴 영상"이면 화면 녹화가 아니라 **가짜 시계로 프레임 단위 녹화**한다(끊김 없는 30fps, 헤드리스, 20초에 2분 안팎):
```bash
node <이 스킬 폴더>/scripts/record.mjs <html> <샷.mjs> <out.mp4> --w 1920 --h 1080 --preview 0,3,6,9   # 미리보기 PNG
node <이 스킬 폴더>/scripts/record.mjs <html> <샷.mjs> <out.mp4> --w 1920 --h 1080                     # 본 녹화
```
- **기본 연출 = 웹뷰 그대로**(`references/example-webview-shot.mjs`):
  페이지 UI가 보이는 원래 아이소 화면, **8배속**. 전체 맵 → 주인공에게 부드럽게 줌인해 따라가기 → 핵심 이벤트는 배속을 1×까지 부드럽게 낮췄다 다시 8×로 → 전체 맵으로 줌아웃해 잠깐 멈춘 뒤 끝. 볼거리는 첫 프레임부터.
  카메라는 view.tx/tz/zoom만 직접 움직이고(줌은 log 공간 보간), 자동 카메라·자동 슬로모션 옵션은 꺼서 대본과 싸우지 않게 한다.
- 시네마틱(원근 카메라 공중 궤도·추격)은 사용자가 따로 원할 때만: `references/example-film-shot.mjs`.
- 영상은 **가장 붐비는 시간대**에서 시작한다. `fastForward`로 하루를 돌려 시간대별 인원·이벤트 수를 재고, 그 몇 초 전부터 찍는다. `RECORD_LOG=1`로 perFrame의 console.log를 보며 타이밍을 맞춘다.
- 영상에서 거슬리는 것: 먼 바닥의 픽셀 반짝임(→ 픽셀 크기 1 + 먼 곳은 안개로 녹이기), 화면 위 각도·디버그 이름표(→ 영상에선 끔), 폭풍처럼 화면을 가리는 날씨(→ 끔).
- 함정: 새 판을 만든 직후엔 좌표가 비어 있어 카메라가 NaN → setup에서 배치 함수 먼저. perFrame은 문자열로 넘어가므로 바깥 변수·import를 못 쓴다. 녹화 전 디스크 여유를 확인한다(프레임 PNG가 수 GB).
- 기본 출력: 1920×1080(세로는 1080×1920), 픽셀 1, 그림자·글로우 켬. 미리보기 PNG로 동선부터 맞추고 본 녹화는 마지막에 한 번.

## 비용 안내
이 규모는 한 번에 크다(HTML 약 120~170KB). 사용자가 비용을 걱정하면 3번에 나눠 만든다:
① 무대+그림체+직접 조작 ② 사람+진짜 규칙 ③ 밤·날씨·이벤트.
